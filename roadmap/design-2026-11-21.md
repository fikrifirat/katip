# Roadmap design (21 Nov 2026)

Written with the *brainstorming* and *writing-plans* method from
[obra/superpowers](https://github.com/obra/superpowers), followed by hand. The plan it produced is
[ROADMAP.md](../ROADMAP.md).

## Intent

Katip is building an open, private legal AI platform for Turkish law firms (and later Dutch
ones), in the spirit of Harvey: an assistant, a case folder, research over statutes and case law,
drafting, and a firm vault. Masking personal data on the device is the trust layer under all of
it and the first thing we sell. The README roadmap was judged "pretty accurate and logical"
(fikri, 21 Nov), so this design adds order, finish lines and evidence to it. It does not replace
it.

## Goals

- One order of work that everything active fits into, with nothing parked (decided 20 Nov).
- A plain finish line for every item, so "done" is checkable by someone who wasn't in the room.
- Each item names the part of the moat it builds: lawyer-graded private data, KVKK-Bench,
  access to sources, the local masking layer, cost and own models, distribution, trust.
- A short, honest note of what recent public discussion confirmed or challenged.

## Non-goals

- Pricing changes. The October price tests stand until pilots give data.
- Weekly task lists. Items are sized in weeks; detail lives in each PR.

## Anti-goals (would make this a failure even if it reads well)

- A redesign of the README roadmap. Small edits only.
- Claims we can't back: no "KVKK-safe", no "no leakage", no dates promised to customers.
- Framing Katip as a masking product only.

## Constraints

- One builder plus Claude sessions; fikri publishes to Hugging Face and arXiv himself.
- No paid credits for this work today; free cloud GPUs for training.
- Weights are CC BY-SA 4.0 and code AGPL-3.0, so the code and weights alone protect nothing.
- Lawyer rules: Av.K. m.35, TBB advertising rules, fee tariff. KVKK guide for lawyers (Sep 2026),
  TBB AI guidance (Aug 2026), NOvA AI recommendations (Nov 2026).

## Approaches considered

1. **Keep the README checklist, add a separate ROADMAP.md with order, finish lines and the
   research check (chosen).** The README stays a product page; the order and evidence live where
   they can grow. Cost: two places to keep in step, handled by linking and by ticking boxes in
   the README only.
2. Rewrite the README roadmap into phases. Rejected: it is the kind of revamp fikri asked us not
   to do, and the README is what visitors and the Claude directory read.
3. A GitHub Project board with one issue per item. Not now: more tooling before the order is
   agreed. Easy to add once this is merged.

## Decided here (Claude's calls, open to correction)

- Four bands: **Now** (to 19 Dec 2026), **Next** (Jan to Feb 2027), **Alongside** (runs all the
  time), **Later** (from Mar 2027). Dates are for our own planning, not promises.
- Research-driven moves: citation checking moves into Now; *Cebindeki hukuk* waits for a written
  bar-rules opinion; a firm setting for "what runs on its own, what waits for a lawyer" is added
  (NOvA asks for exactly this).
- Pilots in Now double as the missing research: the scan could not hear Turkish lawyers.

## Left to the builder

How each item is built: that is decided in its own PR, as before.

## Review note

The superpowers method asks for a reviewer subagent to read the design before planning, and for
the human partner to approve the design. We did a self-review instead, and treat fikri's review
of the PR as the approval step.
